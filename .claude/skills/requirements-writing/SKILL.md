# 要求定義の書き方

## ID と形式（自動検証に使うので厳守）
```
### REQ-001: ユーザーはタスクを追加できる
- 優先度: Must
- 受入基準:
  - AC-001-1: 入力欄に文字を入れて「追加」を押すと、一覧の末尾に表示される
  - AC-001-2: 入力欄が空のときは「追加」を押せない
```
- REQ は見出し（###）で書く。番号は 3 桁、サイクル内で連番
- AC は `AC-<REQ番号>-<連番>`。必ず親の REQ の下に書く
- 非機能要求は `### NFR-001:`。測り方を書く
- 優先度: Must（このサイクルで必須）/ Should / Could

## 受入基準の書き方
- 「（前提）のとき、（操作）すると、（結果）になる」の形にする
- 結果は観察できるものにする（表示される・保存される・エラーが出る）
- 禁止: 「使いやすい」「高速に」「適切に」など、判定できない言葉

## スコープ
- 「対象外」を必ず書く。書かないと設計・実装で膨らむ
- 1 サイクルの Must は、目安として 5〜8 個までにする

## やらないこと
- 実装方法（画面の配置・技術・データ構造）は書かない。それは設計の仕事
- 決められないことを推測で埋めない。「未決事項」に書く
