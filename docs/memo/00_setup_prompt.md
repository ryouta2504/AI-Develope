# 依頼: Human-on-the-Loop 型 AI駆動開発基盤の構築

## 背景と目的
ウォーターフォール型の開発プロセスに、人間とAIの役割分担を組み込んだ開発基盤を
Claude Code の仕組み（サブエージェント / Skills / Hooks / CLAUDE.md / スラッシュコマンド）で構築したい。
AIが単独で成果物を確定させることを防ぎ、重要な判断は人間が承認する「品質ゲート」で品質を担保する。
**ゲートはプロンプト上のお願いではなく、Hooks によって機械的に強制すること。これが最重要要件。**

作業ディレクトリ: C:\Users\User\.claude\projects\AI-Develorer
実行環境: Windows 11（Claude Code は VSCode 拡張から利用）

## 設計原則: Y = F(x)
- Y = 出力、F() = LLM、x = コンテキスト
- Yの精度を保つために、次の2つを制御する
  1. **F の選択**: タスクの性質に応じてモデルを使い分ける
     - 要件分析・設計・最終レビュー → opus
     - 実装・テスト作成 → sonnet
     - 調査・検索・定型チェック → haiku
  2. **x の衛生管理**: コンテキストを汚さない
     - 各サブエージェントには、そのフェーズに必要な成果物だけを渡す
     - フェーズ間の引き継ぎは会話履歴ではなく、ファイル（docs/ 配下の成果物）で行う
     - CLAUDE.md は短く保ち、詳しい手順は Skills に分けて必要な時だけ読み込ませる
     - 調査系の大量出力はサブエージェント内で処理し、親には要約だけを返させる
     - Hooks の出力も簡潔にし、不要なログでコンテキストを埋めない

## 技術スタック（初期想定）
- フロントエンド: React + TypeScript + Vite
- 単体・結合テスト: Vitest + React Testing Library
- E2E テスト: Playwright
- 静的解析: ESLint + tsc（型チェック）+ Prettier
- バックエンド: 未定（要求定義・設計フェーズで決める。基盤側は特定のバックエンドに依存しない作りにする）
- 自動ゲートは npm scripts（test / lint / typecheck / e2e）経由で呼び出し、スタックが変わってもゲートの仕組みは変えずに済むようにする

## 開発プロセス（ウォーターフォール + 品質ゲート）
| # | フェーズ | 担当 | 成果物 | ゲート |
|---|---|---|---|---|
| 1 | 要求定義 | 人間 + requirements エージェント | docs/01_requirements.md | 🔒 G1: 人間が要求を承認 |
| 2 | 基本設計・詳細設計 | architect エージェント | docs/02_design.md（画面・コンポーネント設計、API、技術選定を含む） | 🔒 G2: 人間が設計を承認 |
| 3 | テスト設計 | test-designer エージェント | docs/03_test_plan.md, テストコード(Red) | ⚙ 自動: テストが失敗すること(Red)を確認 |
| 4 | 実装 (TDD) | implementer エージェント | src/ | ⚙ 自動: テスト全通過・lint・型チェック |
| 5 | AIレビュー | reviewer エージェント（読み取り専用） | docs/05_review.md | ⚙ 自動: 重大指摘ゼロ |
| 6 | 最終レビュー | 人間 | 承認記録 | 🔒 G3: 人間が最終承認 |

- 🔒 = 人間ゲート、⚙ = 自動ゲート
- 実装は TDD（Red → Green → Refactor）。テストより先に実装コードを書かせない
- 差し戻し時は該当フェーズに戻り、それ以降の承認は無効化する

## Hooks による品質ゲートの強制（最重要）

### 基本方針
- フェーズと承認状態は状態ファイル `.ai-dev/state.json` で管理する
- フックスクリプトは **Node.js（.mjs）** で書く（Windows で bash/PowerShell の差異を避けるため）
- ブロック時は exit code 2 と簡潔な理由を返し、AI に「なぜ止められたか・次に何をすべきか」を伝える
- ゲート判定ロジックは scripts/ に集約し、フックはそれを呼ぶだけにする（テストしやすくするため）

### 各フックの役割
1. **SessionStart / UserPromptSubmit**
   - 現在のフェーズ・承認状態・次にやるべきことを短く注入する
2. **PreToolUse（Write / Edit / MultiEdit）**
   - G1 未承認 → docs/02 以降への書き込みを禁止
   - G2 未承認 → src/ と tests/ への書き込みを禁止
   - 対応するテストファイルがない src/ のファイル作成・編集を禁止（TDD の強制）
   - Red 未確認のうちは実装ファイルの編集を禁止
   - `.ai-dev/approvals/` と `.ai-dev/state.json` への書き込みを禁止（承認は人間だけ）
   - `.claude/settings.json` と hooks/ スクリプト自体の改変を禁止（AI がゲートを外せないようにする）
3. **PreToolUse（Bash）**
   - リダイレクト・コピー・移動などで保護対象パスに書き込むコマンドをブロックする（ファイルツールを使わない抜け道を塞ぐ）
   - 承認用スクリプトの実行をブロックする（AI が自分で承認できないようにする）
   - `git push`、`--no-verify`、テストのスキップ指定（.skip / .only の追加など）をブロックまたは警告する
4. **PostToolUse（Write / Edit）**
   - 編集したファイルに Prettier と ESLint をかけ、問題があれば簡潔に返す
5. **SubagentStop / Stop**
   - フェーズに応じた自動ゲートを実行する（test / lint / typecheck）
   - 失敗していれば終了をブロックし、失敗の要約だけを返して修正を続けさせる
   - 人間ゲートに到達したら「人間の承認待ち」と明示して停止する

### 人間の承認方法
- 人間は自分のターミナルで `npm run approve -- G1` のように実行して承認する（AI からは実行不可）
- 承認時には成果物のハッシュを記録し、承認後に成果物が変更されたら承認を自動で無効化する
- 差し戻し用に `npm run reject -- G2 "理由"` も用意する

## 構築してほしいもの
1. CLAUDE.md: プロセス全体の要約、原則、ゲートのルール（短く）
2. .claude/agents/: requirements / architect / test-designer / implementer / reviewer / explorer
   - frontmatter で model と tools を最小権限に設定する
   - 各エージェントの入力（読む成果物）と出力（書く成果物）を明記する
3. .claude/skills/: TDD サイクル、要求定義の書き方、設計書テンプレート、React のテスト方針、レビュー観点チェックリスト
4. .claude/commands/: 各フェーズを開始するコマンド、現在の状態を表示するコマンド
5. .claude/settings.json: 上記 Hooks と権限設定（allow / deny）
6. .claude/hooks/: フックスクリプト（Node.js）
7. scripts/: ゲート判定、承認・差し戻しスクリプト
8. docs/templates/: 各成果物のテンプレート
9. tests/hooks/: フック自体のテスト（ゲートが正しくブロック・許可することの検証）
10. README.md: 人間向けの使い方（どのタイミングで何を承認するか）

## 進め方
- いきなり全部作らず、まず「全体設計案（ディレクトリ構成、エージェント一覧とモデル割り当て、
  状態遷移図、各フックの判定ロジック、承認の仕組み）」を提示して、私の承認を得てから実装すること
- 実装は Hooks とゲートの仕組みを最優先で作り、フックのテストが通ってからエージェントと Skills を作ること
- 不明点や選択肢がある場合は、推奨案を添えて質問すること
- 完成後、サンプル機能（例: React の ToDo アプリ）で 1 サイクル通して動作確認する手順を示すこと
